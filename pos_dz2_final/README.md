# ДЗ 2. ПОС

В рамках дз реализовала консольное приложение ПОС на Python. Можно добавлять студентов и критерии оценивания, выставлять, изменять и отменять оценки, смотреть списки студентов, критериев и оценок, рассчитывать итоговый балл и экспортировать результаты в CSV. Использовала стандартную библиотеку Python, дополнительных зависимостей нет.

Выбрала архитектуру Ports and Adapters, разделила код на domain, application и infrastructure. В domain находятся сущности, проверки и логика расчета итоговой оценки. В application находится Gradebook, через который выполняются основные сценарии приложения. В infrastructure находятся консоль, реализация репозиториев и экспорт в CSV. Зависимости направлены внутрь: infrastructure -> application -> domain, при этом infrastructure также может обращаться напрямую к domain. Домен ничего не знает про консоль и файлы. Все зависимости собираются отдельно в bootstrap.py. Данные хранятся в оперативной памяти, так как для этой домашки не вижу смысла подключать БД. После закрытия программы данные не сохраняются, кроме выгруженного CSV.

В доменной модели использовала названия из предметной области: Student, Criterion, Rubric, Evaluation, Score и FinalGrade. Student, Criterion и Evaluation являются Entity, так как у них есть свои идентификаторы. Score является Value Object, так как определяется самим баллом и максимальным баллом критерия. Например, два объекта Score с одинаковыми значениями считаются равными. При исправлении оценки создается новый Score, а не меняется старый. Rubric выделила как агрегат, который управляет набором критериев, выдает им идентификаторы и не дает добавить два критерия с одинаковым названием даже в разном регистре. Студенты и оценки хранятся отдельно, Evaluation связывает студента и критерий через их id.

Основные проверки находятся в домене, а не в консоли. Score проверяет, что балл является числом и находится в диапазоне от нуля до максимума критерия. У критерия должны быть непустое название, положительный максимум и положительный вес. При создании оценки проверяется наличие критерия в рубрикаторе. В Gradebook дополнительно проверяю существование студента и отсутствие другой оценки по этому же критерию. Если оценка уже есть, ее нужно исправить, а не создавать еще одну. Для хранения данных в domain/repositories.py описала интерфейсы StudentRepository, RubricRepository и EvaluationRepository, а их реализации находятся в infrastructure/memory.py. Благодаря этому основная логика не зависит от конкретного способа хранения.

Для расчета итоговой оценки сделала отдельный Domain Service FinalGradeCalculator в domain/grading.py. Он собирает оценки конкретного студента по критериям рубрикатора и передает их выбранной стратегии. Сначала балл по каждому критерию делится на его максимум, затем полученная доля умножается на вес критерия. Сумма таких значений делится на сумму учитываемых весов и переводится в десятибалльную шкалу. Итог не хранится отдельно, а рассчитывается заново при каждом запросе, поэтому после изменения или отмены оценки он обновляется. Если критериев нет или нет учитываемых оценок, результат равен нулю.

Из порождающих паттернов использовала Factory (EvaluationFactory в domain/evaluation_factory.py). Она получает критерий из рубрикатора, создает Score с нужным максимумом и только после проверок создает Evaluation. Так не нужно повторять эту логику в разных местах. Из структурных паттернов использовала Facade (Gradebook в application/gradebook.py). Консоль обращается к нему и не занимается напрямую репозиториями, фабрикой и калькулятором. Из поведенческих паттернов использовала Strategy (GradingStrategy в domain/grading.py). Есть две реализации: AllCriteriaStrategy учитывает все критерии, а отсутствие оценки считается за ноль, GradedOnlyStrategy учитывает только критерии, по которым уже есть оценки. По умолчанию используется первый вариант. Чтобы поменять правило расчета, достаточно заменить стратегию в bootstrap.py, переписывать калькулятор или консоль не нужно.

Также реализовала небольшой DI-контейнер в di.py. В bootstrap.py регистрируются реализации репозиториев, стратегия, калькулятор, фабрика, экспортер и остальные компоненты. Репозитории зарегистрированы как singleton, чтобы при разных операциях использовалось одно и то же хранилище. ConsoleApp зарегистрирован как transient. Gradebook получает зависимости через конструктор. Для экспорта есть отдельный порт ResultExporter в application/ports.py и его реализация CsvResultExporter в infrastructure/csv_exporter.py. При экспорте итоговые оценки сортируются по убыванию и записываются в pos_itogi.csv.

Нейронку использовала для пояснения некоторых архитектурных моментов, иногда для написания отдельных частей кода, юнит-тестов и дополнения моего отчета. Примеры промптов: «Объясни, где лучше разместить интерфейсы репозиториев в Ports and Adapters», «Как правильно разделить ответственность между Domain Service и application?», «Напиши тесты для проверки граничных значений оценки», «Дополни мой отчет пояснениями по коду». Всего получилось 45 тестов. Они проверяют доменную модель, расчет итогов, сценарии Gradebook и инфраструктуру. Все 45 тестов проходят.
